0问题：录像里的两个"时间"为什么对不上

打开一段监控录像，里面其实藏着两个互相不认识的时间：

图 0-1　一段录像里的两个钟：进度条（流内时间）与画面上的电子表（OSD 时间）
钟是什么毛病
流内时间（进度条）文件里每一帧的放映序号：第 N 帧 ÷ 每秒帧数永远从 00:00 开始，不知道"现实里这是几点"
OSD 时间（画面电子表）录像那一刻，监控主机自己的钟显示的时间，被印死在画面像素上这台钟常常从来没对过时：整体慢几分钟、日期错、每天还快/慢几十秒

火灾调查要回答的是："几点几分几秒着的火？"——这是现实世界的时间。进度条答不了；电子表答了也不敢信。

校时，就是给这两个时间之间修一座桥：让软件里任何一帧画面，都能换算出可信的现实时刻，并且把"这座桥是怎么修的"全程留档。

1核心思想：校时 = 造一把"换算尺"

数学上，桥只有一条公式（别怕，就两个数）：

真实时刻 = 起点 offset + 走时速率 rate × 流内毫秒
  • 起点 offset：进度条 00:00 那一帧，对应现实世界的几点几分（含日期）。
  • 走时速率 rate：进度条每走 1 秒，画面上的电子表走几秒。正常钟 = 1.000；每天快 31 秒的钟 = 1.00036。
图 1-1　换算尺：知道起点和斜率，任意流内位置都能换算真实时刻

一把尺子量到底

软件里所有需要时间的地方——图表横轴、光标读数、标签、CSV 导出、报告——全部只允许从这一个换算口拿数（代码里叫 wallMsOf()，行规 C3）。这样就杜绝了"图表说 16:25、报告说 16:27"这种各说各话的事故。

全软件只有一把尺子。校时做的事，就是把这把尺子造准、并留下造尺子的全部证据。

2方法一：自动校时（三点取样拟合）

思路朴素得像称体重：在录像的开头、中间、结尾各截一帧，用 OCR（文字识别）读出画面上电子表的数字，得到三组数据：

取样点流内位置电子表读数（OCR）
开头0 秒08:00:00
中间1800 秒09:00:00.65
结尾3600 秒09:00:01.3

三组数据画在坐标系里是三个点，用最小二乘法画一条"最贴合三点"的直线——

  • 直线截距 = 起点：流内 0 点 = 08:00:00
  • 直线斜率 = 走时速率：3601.3 ÷ 3600 = 1.00036 → 换算成人话："画面时钟每天快 31 秒"
图 2-1　三点取样 + 直线拟合：斜率就是监控钟的快慢

为什么要三个点，两个不行吗

两个点永远能连成一条完美的直线——但你永远无法发现"其中一个点其实是 OCR 看错了"。三个点就不同了：如果某个点明显不在这条线上，它就是野点（异常点），系统会标 ⚠ 自动排除后重新拟合，对话框里还可以人工取消勾选。第三个点是测谎仪。

拟合出的速率若超过 1%（每天快/慢 14.4 分钟），系统直接拒绝应用——物理上没有任何正常的钟能走成这样（见第 7 章），超了必是"看错了"或"文件有问题"。宁可不校，不能错校。

拟合出的 rate≠1，是文件被压缩了吗？

不是。正常录像是实时的：真实世界每过 1 秒录 25 帧，播放也是 25 帧——流内时间和真实时间 1:1 流动，谁也没压缩谁。rate≠1 说的是画面上那个电子表自己走得不准（监控主机的钟快/慢），跟文件无关。真正被压缩的文件长什么样，见第 5 章。

3方法二：北京时间对时（同框拍照）

第 2 章解决了"钟走得快不快"，但还有一个独立的问题：钟整体偏了多少。很多监控主机从装上的那天起就没对过时，整个钟慢十几分钟是常事。

图 3-1　取证惯例：手机显示标准北京时间，与监控屏幕同框拍照

把照片导入软件，依次框选两个时间 → OCR 自动识别 → 相减：

偏差 = 北京时间 − 监控时间 = 12:39:41 − 12:25:47 = 慢 13 分 54 秒

这个偏差叠在第 1 章的尺子最外层：北京时间 = 监控墙钟 + 偏差。确认卡上两个时间可以直接人工修正（OCR 偶尔会认错数字），原文、截图、框选坐标全部随案件留档——原文永不修改，修正留痕。

精确度边界：对时补的是"拍照那一刻"的偏差。如果监控钟还在漂移（每天快 31 秒），而照片是案发后 5 天才拍的，那案发那一刻的真实偏差和拍照时测到的偏差之间，隔着 5 天 × 31 秒 ≈ 2.6 分钟的累积漂移——拍照离案发越近越准。
2026 年 8 月某火灾案：C01 机位同框对时，测出监控慢 13 分 54 秒。报告中这一路的"显示时间取样"列写的就是经人工修正后的 12:25:47，OCR 原文（12:25:42，识别有误）作为留档标注一并呈现——修正值与偏差值 834 秒完全自洽。

4方法三：同事件对时（接力链）

有些摄像头没法直接对时：画面里没电子表、也没法拍同框照。但火灾现场常常有天然的"对时信号"——两路监控拍到了同一件事：同一声爆燃、同一扇门被推开、同一个人跑过巷口。

做法：在已校时的"参考路"和没校时的"目标路"上，各标出这件事发生的时刻 → 两个时刻对齐 → 目标路的时间轴整体平移过去。标两个以上事件，还能连"快慢"一起拟合出来。

图 4-1　接力链：C01 有照片对时，C02 借 C01，C03 借 C02
同一案件：C02 无电子表，靠两段录像里"同一声响"与 C01 对帧，误差 ±0.3 秒（报告写"一致（±0.5 秒内）"）；C03 再借 C02 的对齐结果。报告"时间校准"章末尾如实写出接力关系：C03 → C02 → C01 → 标准授时。

5特例：被压缩的录像（时间重建）

有些 DVR 为了省硬盘用抽帧录像：没动静时每秒只录 12.5 帧，有动静才录满 25 帧；导出时统一按 25 帧重新打时间戳。后果是——

真实世界 103 分钟的内容，被压进了 74 分钟的流内时间里。流内 60 秒 ≠ 真实 60 秒，而且压多压少随时段变化。
图 5-1　抽帧录像：真实 103 分钟 → 流内 74 分钟

分段查表：一把尺子换成一排尺子

时间重建用"两级采样"：先粗采样找出"哪里变速了"（边界），再在边界附近加密取样确认，最后生成一张分段时间映射表——每段内部仍是"起点+速率"的小直线，段与段之间允许跳变。

图 5-2　分段查表：段内是直线，段间允许跳变；竖线缺口 = 监控关机/漏录的真实空档

段间的竖直跳变不是错误，是如实记录：监控有缺口（关机、漏录、循环覆盖）是常态。打开这种文件时软件会弹出缺口提示，缺口明细同时写进报告——少了哪段时间，调查员必须知道。

6方法四：继承（拼接产物自带校时）

前处理"素材转码拼接"把多段素材合成一个文件时，软件会把每一段的校时信息写成一个小小的伴生文件（.lumencal.json，行话叫 sidecar）跟着产物走：

  • 每段的墙钟起点 + 走时速率（按画面 OCR 时间锚定）
  • 重叠修剪了多少、哪段转码失败被丢弃、缺口的起止和时长——全部留痕

打开拼接产物时，这份信息自动继承为分段校时表，不用再做一遍校时。前处理的证据摘要（"导入 N → 输出 M，缺口逐条明细"）与这份校时同口径，两边数字永远对得上。

7专题：电子表为什么会不准（晶振与 RC）

电子表的心脏：每秒振 32768 下的小石英片

监控主机里管时钟的是一颗 32.768 kHz 石英晶振。为什么是这个怪数字？因为 32768 = 2¹⁵，电路数它振满 32768 下，就当 1 秒。

  • 石英片振得比设计值略快（比如每秒 32768.5 下）→ 表走快（每天快约 1.3 秒）
  • 振得略慢 → 表走慢
纠正一个流传很广的误解："晶体会衰减，所以钟总是越来越慢"——不对。走快走慢都可能，没有单向变慢的物理规律。
影响因素方向量级说明
① 出厂底子可快可慢每天 ±0.4~1.7 秒晶体切割有误差，这颗生而就快、那颗生而就慢，随机，跟随一辈子
② 温度只会推向慢机房酷热时每天再慢几秒音叉晶体在 25°C 时振最快，冷了热了都变慢——但若出厂底子偏快，热天只是"没那么快"，仍可能在走快
③ 老化（"衰减"）可快可慢每年 1~2 分钟以内存在但极小、方向不定，头一年变化多点，之后基本稳定

为什么有的监控钟慢得离谱：RC 振荡器

芯片干活需要"心跳"节拍。产生节拍最准的办法是石英晶振，最便宜的办法是 RC 振荡器——用一颗电阻（R）加一颗电容（C）搭的节拍器：

图 7-1　两种"心跳"：音叉式 vs 气球水管式

山寨 DVR 用 RC 纯粹是为了省一毛钱（晶振要外焊一颗元件，RC 能集成在芯片里）——"能显个数就行，准不准没人管"。

量级感：每天差多少算正常

钟的种类每天误差上限结论
正常石英晶体几秒以内✅ 正常
烂晶体 + 极端温度十几秒边缘，仍属晶体物理范围
RC 垃圾钟（山寨机）十几分钟硬件垃圾，不是"衰减"
超出以上（每天差几十分钟）—物理上不可能 = 必是 OCR 看错 或 文件被压缩
增城案 C03 机位：同事件对时拟合出"每天快 10 分钟"——比最烂的石英晶体还烂 40 倍。所以结论不是"钟快"，而是这路文件的时间轴本身有压缩特性。两路独立拟合结果一致，正说明"错得很稳定"——错的是文件，不是识别。

8可靠性设计：三道闸门与留档

校时结论是要进报告、上法庭的。系统用三道闸门把住"宁可不校、不能错校"的底线：

图 8-1　三道可靠性闸门

留档：每个结论都能回溯到原始证据

  • OCR 原文、证据截图、框选坐标随校时结果一起存进 .vla 与案件目录，原文永不修改；人工修正只改"修正值"，原文一并呈现
  • 修正参数可审计、可关闭（rateApplied=false 即回到未修正状态）
  • 每次校时操作记录"操作时刻"时间戳
  • 同事件接力：事件名必填、误差逐跳累加、报告独立小节如实呈现接力链
  • 报告"时间校准"章用白话写校准方法、差值与结论，不堆参数

9生效面与取证红线

校时一旦采用，这些地方全部同步生效

位置表现
案件树视频条目旁亮 ⏰ 徽标
图表时间轴 / 光标 / 标签悬停显示真实时刻（已做北京时间对时则显示北京时间）
CSV 导出时间列同口径换算
截图文件名自动带校准后北京时间；OSD 角标显示北京时间
报告第四章"时间校准"：白话方法说明 + 六列对照表 + 接力链小节

前处理产物命名自动按校时墙钟命名：CAM01_20260722_172528-173541.mp4

没校时的视频行为完全不变（图表照旧显示流内时间）——校时是可选增强，不是强制。

取证红线（不可逾越）

OSD 画面像素永不修改。画面是证据，动一个像素都不行。软件做的永远是"建换算模型"，不是"改画面"；源文件永不写入；所有修正只动模型参数，且全程留痕、可关闭、可回溯。
一句话总结：正常录像的流内时间就是真实时间的脚步（1:1），自动校时量的是"画面里那个挂钟准不准、起点在哪"；只有抽帧录像才存在真·压缩，而它走时间重建那条路。所有结论留档，所有误差如实呈现。

10术语小词典

流内时间
视频文件自己的播放进度时间，从 00:00 起算。由帧序号÷帧率决定。
OSD 时间
监控主机印在画面像素上的电子表读数（On-Screen Display）。是"监控的钟"的历史记录。
北京时间 / 墙钟
现实世界标准时间。软件内部叫 wallMs（墙钟毫秒）；北京时间 = 墙钟 + 对时偏差。
偏移 offset
换算尺的起点：流内 0 点对应的真实时刻。
速率 rate
换算尺的斜率：流内每走 1 秒，OSD 走几秒。1.00036 = 钟每天快 31 秒。
拟合 / 最小二乘
给几个取样点画一条"最公平"直线的数学方法。
野点
明显偏离直线的取样点（多半是 OCR 认错了），自动标 ⚠ 排除。
锚点 / 同事件对时
两路监控拍到同一事件的时刻对。把已校时路的"准"传递给未校时路。
接力链
锚点传递形成的路径，如 C03 → C02 → C01 → 标准授时。允许多跳，禁止成环。
分段表 / 时间重建
变速/抽帧文件的校时方式：整片切成若干段，每段一把小尺子，段间允许跳变。
缺口
监控没录上的真实时间段（关机/漏录）。如实提示并写入报告。
sidecar（.lumencal.json）
拼接产物的伴生校时文件，打开产物时自动继承成分段校时。
晶振 / RC 振荡器
时钟芯片的"心跳"来源。晶振准（每天几秒），RC 不准（每天能差十几分钟），山寨机为省钱用 RC。
.vla
本软件的分析结果文件（含校时模型与全部证据留档）。
