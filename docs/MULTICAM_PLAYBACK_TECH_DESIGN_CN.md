# 多视频同步播放（多机时间线合并）技术方案

> 文档版本：v0.1（调研草案）

---

## 1. 背景与需求

火调现场常见**多机位同时段监控**（如增城案：正门/后门/厨房多路）。当前
LumenArc 单视频播放：看 A 机 03:00 的画面后，要人工记住时刻再切 B 机找同
时刻——**跨机位"同一墙钟时刻各机画面"对比**全靠人脑拼接。

需求（用户口述，2026-08-18）：
1. **多路视频同时播放**（同屏网格），各路按**墙钟对齐**（不是各自流内
   00:00 对齐）——A 机 03:00:00 时 B 机也显示它校时后的 03:00:00；
2. 与**多机时间线合并**：现有多机时间线条（只读墙钟块位视图）升级为
   播放控制面——共享游标拖动即多路同步 seek。

## 2. 现状盘点（代码事实，均有落点）

| 资产 | 落点 | 与本需求的关系 |
|---|---|---|
| 单路播放引擎 | `infrastructure/ffmpeg_video_engine.{h,cpp}`（IVideoEngine） | 多实例即可多路；每实例自持解码/音频线程 |
| 倍速播放 | IVideoEngine::setRate（0.25x-8x UI 已暴露，音频重采样随速变调） | 同步播放可直接继承 |
| 多机时间线只读视图 | `multicamview.{h,cpp}`（MultiCamDialog，v1.3 M3） | 墙钟块位/重叠红带/缺口灰纹已有；**只读对话框**，双击仅发 laneActivated |
| 机位墙钟数据装配 | `app/cam_timeline.{h,cpp}` buildCamLanes | 逐路读案内 .vla 校时 → wallStartMs/wallEndMs |
| 校时 SSOT | `domain/time_calibration.h` wallMsOf/streamMsOf（分段重建兼容） | 流内毫秒 ↔ 墙钟毫秒双向映射现成 |
| 案件视频登记 | CaseVideoRef（id/originalPath/vlaRelPath/cameraLabel/hasCalibration） | 机位清单与校时徽标现成 |
| 主时钟/状态机范式 | AnalysisTaskService（R7 显式状态机先例） | 同步播放服务照此模式 |
| GPU 显示管线 | P-29 已拍板未施工（DEVELOPMENT_PLAN_V1.6） | 多路 1440p CPU 缩放的性能兜底 |

**现有视图的关键数据缺口**：`CamLane.wallEndMs` 由 `.vla 已分析时长`推出
（块位宽度的设计语义=分析覆盖范围），**不是视频真实全长**。同步播放需要
真实全长（probe duration），装配层需扩展字段。

## 3. 总体架构（草拟）

```
┌─ ui ────────────────────────────────────────────┐
│  MultiCamPlaybackDialog/Dock（多机播放面板）      │
│   ├─ CamTileWidget ×N（轻量帧显示瓦片，非 VideoWidget）│
│   └─ MultiCamTimelineBar（现只读视图升级：共享游标+播放键）│
├─ app ───────────────────────────────────────────┤
│  MultiCamSyncService（新增，R7 状态机：            │
│    Idle→Loading→Ready→Playing/Paused→Ended）     │
│   ├─ 主时钟（单调时钟 + 主路音频锚定）              │
│   ├─ 每路 streamMs = cal.streamMsOf(wallMs) 换算  │
│   └─ 周期性纠偏（位置轮询 → 丢帧/微 seek）          │
├─ infrastructure ────────────────────────────────┤
│  IVideoEngine × N（R4 引擎中立，禁止 UI 直触实现）  │
└──────────────────────────────────────────────────┘
```

### 3.1 同步模型（核心决策面）

- **统一墙钟轴**：所有路映射到墙钟毫秒。T(wall) 时刻第 i 路应显示
  `streamMsOf(T)` 处的帧；该路在此墙钟区间无数据（缺口）→ 瓦片显示
  "无信号"占位，不错位硬播。
- **主时钟**：v1 用单调时钟（QElapsedTimer + 播放起点墙钟），**不锚定某路
  音频**（多路音频互不相关，锚定单路会让其他路被动漂移）；音频只开
  **一路**（用户选定的"主听音路"，其余静音——多路混音对取证查看无意义）。
- **纠偏**：每 250ms 轮询各路 position()，与主时钟换算值偏差 >80ms
  （@20fps 约 1.6 帧）即 seek 纠正；<80ms 由引擎自由运行。长 GOP 素材
  （明景类 12.5s）seek 代价高 → 纠偏阈值与 GOP 联动放宽（§7 风险 R-2）。
- **倍速**：主时钟按 rate 缩放推进；各路引擎各自 setRate（既有能力），
  纠偏阈值不变。

### 3.2 UI 形态（草拟）

- 入口：现"多机时间线(&M)..."菜单升级为"多机同步播放(&M)..."；
  <2 路已校时维持置灰（既有判定复用）。
- 布局：顶部瓦片网格（1×2 / 2×1 / 2×2，按路数自适应，上限 4 路 v1）；
  底部时间线条（现 MultiCamViewWidget 画风复用：块位/重叠/缺口 +
  **共享墙钟游标**，拖动游标 = 全路 seek；游标处各瓦片联动）。
- 瓦片：**轻量新控件**（QImage paint + 路名/墙钟 OSD/无信号占位），
  不复用 VideoWidget（其 ROI/放大镜/快照叠加是多路场景的噪音与状态负担）。
- 音频路由：瓦片点击激活 = 主听音路切换（🔊 角标），其余路 setVolume(0)。

### 3.3 与既有模块的边界

- UiState / VideoSessionManager / ChartPanel 等**单视频分析栈完全不动**；
  多机播放是独立面板，双击瓦片可"回到单路分析"（既有 openVideo 路径）。
- 校时数据只读消费（.vla SSOT，R5）——本功能不写任何案内文件。

## 4. 性能预估（诚实账）

| 场景 | 解码负载（软解） | 判定 |
|---|---|---|
| 4× 640×360 DVR | ~4×8% CPU（i7 级） | ✅ 轻松 |
| 4× 1080p | ~4×25% | ⚠️ 可行，需关无关面板 |
| 4× 1440p（明景类） | ~4×40%+ 且每帧 CPU 缩放 ~10ms | ❌ 需 P-29 GPU Stage 1 先行或限 2 路 |

v1 建议：**1440p 及以上限 2 路**，≤1080p 限 4 路（瓦片按显示尺寸请求
缩放帧，引擎已有缩放路径）；P-29 落地后放开。

## 5. 测试策略

- domain 级：streamMsOf/wallMsOf 双向映射在分段校时下的一致性（既有
  piecewise 套件扩断言）；主时钟换算纯函数单测。
- app 级：MultiCamSyncService 状态机对抗测试（一路加载失败/一路缺口区间/
  纠偏阈值触发/倍速切换）——用假引擎（IAnalysisEngine 假实现先例）。
- UI 链：ui_chain 套件扩"开面板→播→拖游标→切主听音路→关"无崩溃断言。
- 真机点检：4 路 1080p 30min 连续播放漂移量（目标：全程纠偏后 ≤100ms）。

## 6. 拍板点（Q 项）

- **Q1 入口形态**：独立对话框（推荐，不动主窗布局）vs 主窗内嵌 Dock？
- **Q2 路数上限**：v1 限 4 路（推荐，含 1440p 限 2 路的性能闸门）？
- **Q3 音频策略**：单路主听音（推荐）vs 混音？
- **Q4 未校时路**：排除在外（推荐，校时是墙钟对齐前提）vs 允许手动
  指定偏移临时加入？
- **Q5 游标粒度**：拖动游标实时追逐（scrub 模式复用，推荐）vs 松手才 seek？
- **Q6 与 P-29 的先后**：接受 1440p 限 2 路先行（推荐）vs 等 GPU 管线？

## 7. 风险与应对

- **R-1 多实例解码稳定性**：引擎长期单实例运行，N 实例并发需压测
  （线程命名/全局 sws/av 无共享状态，理论安全；真机 4 路 1h 老化）。
- **R-2 长 GOP seek 风暴**：纠偏触发 seek 在 12.5s GOP 素材上 = 解码至
  多 250 帧 → 纠偏阈值按 GOP 自适应（probe 关键帧间隔已知，§46 探测
  修复后可用）；>4s GOP 的路纠偏阈值放宽到 500ms 且只在偏差持续增长时纠。
- **R-3 校时精度天花板**：墙钟对齐精度 = 各路校时精度（OCR/手动采样
  误差率 rate±0.4% 级）。30min 偏移可达秒级——**UI 必须明示"对齐精度
  取决于校时"**，报告引用时同样注明（取证口径）。
- **R-4 音频漂移**：主听音路引擎自带背压/重采样已验证（v1.5+），其他路
  静音无此问题。
